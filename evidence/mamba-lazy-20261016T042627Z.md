# Candidate: mamba strategy extra_buffer_lazy

Date: 2026-10-16 ~04:23–04:26 UTC. Launcher:
`configs/docker/candidates/qwen27b-mamba-lazy.sh`. One launch, no retry.
Not promoted.

## What changed

- `--mamba-radix-cache-strategy extra_buffer` → `extra_buffer_lazy`
  (4 state slots/request instead of 5; confirmed in the startup warning)
- `--max-running-requests 80`, set above the expected mamba cap so
  DFLASH's default of 48 would not hide the raise. Everything else
  matches the promoted config (mem-fraction 0.85, DFLASH D=4, ratio 2.0).

## Startup

The engine capped admission itself:

    max_running_requests is capped to 57 by the mamba state cache
    (max_mamba_cache_size=229, 4 state slots per request).

`/server_info` still reports the requested 80. The startup line
`max_running_requests=57` is the effective cap. Do not read the
requested value as the live admission limit.

| Pool | promoted c12 (extra_buffer) | this candidate |
| --- | --- | --- |
| Mamba states | 254 (5 slots → cap would be 50) | **229** (4 slots → cap **57**) |
| DFLASH intermediate | 3.66 + 0.07 GB | **16.31 + 0.32 GB** |
| Shared KV pool | 708,463 | **425,330 (−40%)** |
| Effective admission | 12 (explicit) | **57** (mamba-bound; requested 80) |
| Free GPU mem after init | 10.89 GB | 8.97 GB |

The intermediate SSM pool scaled with the higher cap and ate both KV
tokens and mamba states (254 → 229). The cap did rise, from the
DFLASH default of 48 and from the production cap of 12, to 57.

## Prefix reuse

Same probe as the c12 baseline: second request cached **2,688 / 2,704**
tokens; unrelated prefix cached 0. `extra_buffer_lazy` did not break
prefix reuse. Evidence:
`mamba-lazy-prefix-reuse-20261016T042522Z.json`.

## Load

Full benchmark 9/9, zero retractions, `/health` 200 after, GPU memory
flat (85,081 → 85,083 MiB). Because the cap is 57, c45 actually ran
concurrently instead of queueing: aggregate 1,942 tok/s, decode p50
65 tok/s, TTFT p50 0.99 s (c12 config at the same scenario: 1,034 tok/s,
decode p50 107, TTFT p50 3.12 s). That is the admission difference,
not a free lunch — each of 45 users gets ~9.4k tokens of the 425k pool
versus ~59k for each of 12 on the promoted config.

## Verdict

The backlog question is answered: lazy raises the mamba-bound cap
(4 slots/req, effective 57) and prefix reuse still works. It is not a
better production config than cap-12 `extra_buffer`: the KV pool falls
40% because the speculative intermediate pool grows with the cap.
Left unpromoted.
