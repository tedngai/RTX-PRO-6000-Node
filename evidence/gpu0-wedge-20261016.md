# GPU 0 vGPU compute-instance wedge (2026-10-16 ~02:49 UTC)

## Symptom
Every SGLang launch after 02:49 UTC fails at CUDA init:

    RuntimeError: Failed to get GPU memory capacity from nvidia-smi.
    torch.cuda.mem_get_info() fallback also failed:
    CUDA error: CUDA-capable device(s) is/are busy or unavailable

## Timeline (all from logs/qwen27b_sglang.log and launch_qwen27b.out)
- 02:27 / 02:33 / 02:39 UTC — launches SUCCEED (same script, same image,
  same MIG-UUID resolution). Each logged the normal "Falling back to
  torch.cuda.mem_get_info(). Reported ... [97838] MiB" line.
- 02:49 UTC — `docker stop qwen27b-sglang` (graceful SIGTERM, exit 0,
  442,745-token pool / ~90 GB in use) to switch from the DFLASH-4+r2
  candidate to the promoted main config.
- 03:02, 03:10, 03:20 UTC — 3 launches, ALL fail identically at CUDA init.
- Direct probes: `torch.cuda.is_available()` -> True, `device_count()` -> 1,
  but `torch.cuda.mem_get_info()` raises cudaErrorDevicesUnavailable.

## Root cause
Environment is a VMware Horizon VDI guest; both GPUs are vGPUs. GPU 0's
compute instance is wedged: CUDA context creation reports available but the
device-memory query through the compute engine fails. GPU 1's identical
MIG 4g.96gb slice works fine (True, 96 GB), ruling out a generic driver/CUDA
failure. GPU 0 is NOT resettable from inside the guest:

    nvidia-smi --gpu-reset -i 0  -> "GPU Reset couldn't run because GPU
      00000000:03:00.0 is in vGPU mode."
    nvidia-smi mig -dci ...      -> "Insufficient Permissions"

## Recovery
Requires a Horizon-host vGPU compute-instance reset or a VDI guest reboot
(re-attaches a fresh vGPU compute instance). Not possible from inside the
guest.
